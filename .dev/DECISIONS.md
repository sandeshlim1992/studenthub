# Decisions

What was decided for Student Hub and why, newest at the bottom. The current state is in `.dev/NOTES.md`.
Never put passwords, tokens or keys in this file.

- Devcontainer (Option A) is the standard setup; manual setup is fallback only
- `develop` is the only branch; merge commits only (no squash/rebase) — keeps Taxil sync working
- Prefer new files over editing Zammad's originals (fewer upstream merge conflicts)
- Don't edit `.github/workflows/`
- Use Node 24 (ignore `.mise.toml`)
- Browser tests: Playwright in `e2e/` with its own `package.json` and lock file (not the app's), Chrome from the
  container; staff answer through the REST API with web messages; logins only in git-ignored `e2e/.env`
  (README → Browser tests)
- AI agents propose changes and wait for approval before editing code; one yes covers the whole task
  (rule in CLAUDE.md)
- `auto_wizard.json` is dev-only: removed from the repo, never on test/production servers
- Test server pulls from this repo (read-only deploy key), not from Taxil's
- Servers are updated only with `script/studenthub/deploy.sh` (README → Deploying to the servers),
  never with a manual `git pull`; production gets the exact commit tested on the test server (`--ref`)
- Staff work in the new UI, served at `/` since 11 Oct (Zammad's `/desktop/…` redirects there, the classic UI is at
  `/app`) → new staff features go there first. Every file changed for the move and how to undo it:
  `.dev/new-ui-at-root.md` (restore tag `before-new-ui-at-root`)
- Feedback Collection is native (replaces the PHP `feedback.php` add-on); sends through a Zammad email
  channel; admin page in `/manage` (README → Feedback Collection)
- Ticket Approvals: the agent picks any manager (anyone with the Managers role, whatever the team); on/off
  switch in `/manage`; the ticket's state never changes. While waiting the ticket sits in the system
  group "Managers" (nobody has group access) and only the chosen manager + the agent who asked can read it
  (TicketAccess, not group access); team and owner come back with the decision. SLA pauses while waiting
  (admin switch, on by default). Managers without another staff role get only the decision card and their own
  dashboard (README → Ticket Approvals)
- Manager dashboard = design "3C-5" from the design canvas (<https://claude.ai/artifact/WR4v15cTSdT7Ja5W5YoHiE>):
  one request at a time, decided on the dashboard; empty = All caught up + Your month in review. Design
  context for Impeccable lives in `PRODUCT.md` (repo root, not committed yet: excluded in `.git/info/exclude`)
- Teams views are generated by Student Hub (one per group, open tickets, grouped by agent, unassigned tickets
  always first); every view has a per-agent Group by + sort stored in the agent's preferences
- Student Hub views keep fixed positions (Teams from 5000, Sites from 9000, manager sites from 9500) and are saved
  without Zammad's renumbering of the other overviews (`Studenthub::TicketViews.update_view!`). Before, any change of
  order (a new or renamed team or site, or Ticket Approvals taking the Managers group) started a sync that never ended
  and kept puma near 100% CPU (work PC, 11 Oct; it also stopped all live updates there)
- Who sees Teams: agents get the groups their roles give them (the plain Agent role gives Service Desk, VLE and
  Infrastructure, so most agents see 3); users with the Managers role get none unless they are admins; admins see
  all. For that the Teams sync makes the Admin role an agent role with full access to every team group
- Teams views are locked on `/manage/overviews` ("Managed automatically": no on/off, reorder or delete),
  because the sync resets them; remove one by switching off its group
- Sites views (called Institutions in the code): one per active organisation (its customers' open tickets), Admin role
  only, kept in step
  with the organisations and locked like Teams (replaced the LSST / UKBC / FSB views by campus)
- The approval overviews (Awaiting my approval, Sent for approval) are system-managed like the Teams views:
  on/off follows the Ticket Approvals switch, roles are fixed (Managers / every agent role except Managers and
  Admin), locked on the
  Overviews page, hand changes undone by the background sync. The old "Managers Approval" overview stays off
- Recent keeps tickets, customer/organisation/search tabs and saved New ticket drafts; untouched New ticket tabs
  close when left, typed ones ask "Save draft / Discard"; newest tab on top (a new tab opens at the top, drag still
  reorders)
- Students on the ticket screen: compact header without actions, the docked reply box (reply only, Send saves),
  no message actions
- Request forms: one per Category › Sub-category, draft then publish (README → Request forms; design doc
  <https://claude.ai/code/artifact/d646f913-e0b6-482d-b929-13c9744ddc27>). A form is items in order: its own
  questions (stored by Student Hub in `studenthub_request_answers`, not Zammad fields, so publishing never restarts the
  app; they can't drive triggers, overviews or reports), existing Zammad fields (applied by a locked core workflow,
  checked on the server), headings and notes. The server writes a Request details block at the top of the first
  message. Decided 10 Oct: title = the sub-category; agents' New ticket keeps the Zammad fields and gets a separate
  Request details panel for the form's own questions; own questions never in Details and not corrected by agents;
  `admin.request_forms` is the only permission; up to 20 questions and fields per form
- Student wizard's Details step = design D + card D1 of <https://claude.ai/artifact/UeLPcFJBkKoFFxhtektpDb>: a
  "Your request" card (steps taken, each with Change, then Details) beside the form, stacked when the wizard is
  narrow (container query). With a request form the Subject sits at the top of the form and there is no Description
  (the first message is the Category / Campus lines and the Request details block); without one, Subject and
  Description as before. The admin preview shows the same. Questions and fields can be Half width (two columns from
  32rem of form width, `width: 'half'` in the item; the whole width is the default and not stored)
- New UI look follows the UI/UX Pro Max "minimal Swiss" guidance, all accents from the application colour
  (UI/UX Pro Max is a user-level Claude Code plugin; reinstall after a container rebuild)
- New UI design: Halo-style (mockup <https://claude.ai/artifact/6H4uc22Wb4zTiUfy3PhXfj>), application colour chosen
  by admins under Branding (default navy), staff top bar, ticket screen restyled but not restructured, student
  portal keeps Taxil's layout with the new look; built on branch `studenthub-newUI`, one local commit per step
- Managers with no other staff role raise tickets only with the Customer role: student-style New ticket (copy of the
  "How can we help?" card and categories, application colour, no "Talk to Student Support"), ticket is theirs
  in a customer group; without the Customer role no New ticket button and the page is refused
- Top bar crumbs: Tickets pages, New ticket, Dashboard, and Administration / Reporting (their own page trail, moved
  from above the page by `LayoutContent`); the navigation panel shows the user's role (Admin, Agent, Manager, "& Manager")
- Members (top bar button + Members page, README → Members): agents and admins only; online = active in the last
  5 minutes (session touched by any request), offline shows Zammad's last login
- No self-registration (setting off by migration, Register link removed); notifications are in-app and silent (no
  browser pop-up or sound, both UIs)
- Manager sites: admins assign organisations to managers (Ticket Approvals admin page) → read access to those tickets,
  a site view under Sites for those managers, My sites stats on the manager dashboard; teams unchanged
- Checklists are added by Student Hub, not by triggers: admins pick Category › Sub-category pairs per checklist on
  the Checklists page; the server adds it when a ticket is created there or moved there without a checklist, never
  replacing one (README → Checklists added automatically). The four "Checklist : …" triggers keep only their
  `checklist-checd` tag (other triggers react to it); their loopback webhooks are off (migration, 11 Oct). Tickets
  that were in the sub-category before get it from their Checklist tab (Add this checklist), not automatically
- Checklists are admin-made and admin-assigned (13 Oct): on a ticket agents only tick and untick; adding, editing,
  reordering, deleting items, renaming, removing, empty checklists and templates need `admin.checklist`, enforced on the
  server for the new UI, classic UI and API (`Studenthub::ChecklistRules`); agents may add only the checklist assigned
  to the ticket's sub-category. Checklist tab = design B ("steps timeline") of
  <https://claude.ai/artifact/W3yaJpnvhharThcMzzRrAW>
- Classic features move to the new UI as pages that read through small Student Hub endpoints and save through
  Zammad's own REST API (its checks and permissions apply); settings a page doesn't know are kept as they are
- Customer feedback is for admins only (`admin.feedback_collection`: sidebar panel in both UIs and the API); the
  internal note with the rating is off by default
- Dashboard: agents get a Briefing (own figures from Zammad's stats, plus one card per team they can read with its
  unassigned open tickets), admins a Team overview (open by team, SLA, unassigned, trend, sites, channels, rating,
  activity), managers their approvals; users with more than one switch between Team overview / My work / Approvals
  (kept in the browser); "open" counts every state except closed/merged, so "5. Resolved" is open
- Students get their own ticket column (summary, progress steps, files, close / reopen / rate) instead of Details
- Staff ticket screen = option B of the design board (<https://claude.ai/artifact/SKNJWEgQtaeSMKD3GwPTZJ>): the queue of
  a view on the left (J / K, next ticket after closing), compact header (actions as icons, ⋯ Merge, Close), reply box
  docked under the messages (option 1 of <https://claude.ai/artifact/3JzJfNe582BUwGe1knpdLc>: Reply / Internal note /
  Phone call tabs above a text box that takes the mode's colour, Zammad's editor in the same box once you write
  without its channel row and "Text" label, toolbar under the text with the common tools and the rest under ⋮,
  Send = Update, Reply all in the box; messages have no Reply / Reply all of their own, no pinned reply panel), panels
  in one column on the right
  behind four tabs Ticket / Student / Checklist / Approval (no Organization tab; occasional panels add a tab while they
  apply), Update at the foot of that column (unsaved note + Discard, After update, Update; Zammad's bar only while the
  column is collapsed); students and managers-only keep the sidebar on the left and Zammad's bar. Ticket tabs still go
  to Recent (Zammad's tabs left as they are)
- Agents' Reply goes by Email (default; in the student's email thread when there is one) or Web (portal only), picked
  next to Send. Email is greyed out when the student or the ticket's group has no address. Zammad's web type is open
  to agents for this (`plugins/web.ts`, so it is also in Zammad's own type list and on mobile). A web reply emails the
  student a notice with a link (trigger "Agent replied on the web : Email Notification to Customer", created once by
  `Studenthub::WebReplyNotice`; admins edit or switch it off under Triggers; the notice is an internal message)
- Navigation = design C of <https://claude.ai/artifact/N1Lp8tk5n2cT3CfjS9VmhL>: rail in the application colour
  (always shown, short labels) + light panel (role, section name, ticket views on Tickets and ticket screens, Recent,
  collapsed after each sign-in and kept as the user leaves it until signing out);
  on the Dashboard the panel has the dashboard switch, Needs attention (fixed list of overview links the user has) and
  who is online instead of Recent (Recent from the rail there); the page's own switch shows only while the panel is
  hidden; on Members the panel filters the page (Show / Roles / Teams with online counts, no Recent either) and the
  page groups by role by default (Sort by Name / Last active kept in the browser); hiding the panel reuses Zammad's
  collapsed primary sidebar state; the Tickets page lost its own views column; no resizing. On the Knowledge Base
  the panel has the title filter and category tree (no Recent; New category and language above the page, the page's
  own column only while the panel is hidden). Administration and Reporting have no panel (only Recent was in it);
  Recent from the rail there, no Show panel
- Exchange, S/MIME and PGP stay, with pages in the new UI; visible "Zammad" text is now "Student Hub"
- The Dashboard is registered in production builds too (Zammad only had it in development and test)
- Staff start on the Dashboard (`/` sends agents, admins and managers there); students start on their ticket list
- Student Hub migrations always create their tables and columns, but records (roles, settings, overviews) only on
  a seeded database (`Studenthub::Setup.seeded?`). On a new database (devcontainer, CI) migrations run before the
  seeds, so `lib/tasks/studenthub_setup.rake` runs `Studenthub::Setup.ensure_all!` after `db:seed` (not in test:
  spec support re-runs the `*/setup.rb` it needs after the test DB reset; Zammad's seed list is fixed, so no seed files)
- Reporting = design A ("filter column") of <https://claude.ai/artifact/UQdd5UKVEdKBRCkbo85fMW>: report profiles in
  one list, not grouped by LSST / FSB / UKBC (admins make every profile); every figure comes from Zammad's reporting
  API, so it needs Elasticsearch (README → Reporting)
- Approval tab (staff ticket screen) = design B ("timeline") of <https://claude.ai/artifact/JaKwPJH4KdCuDoxQDgqC4j>:
  a state chip, the form (open until something was sent, then behind "Send for approval again") and every request
  and decision newest first, the waiting step carrying Withdraw or Approve / Deny
- No Zammad update is coming (decided 12 Oct): security fixes go straight into Zammad's files, marked with a
  "Student Hub:" comment, and dependencies are patched here. Snyk (VS Code, Open Source + Code Security) is the
  checker; its Code findings in Zammad's files were reviewed on 12 Oct: class-name lookups tightened
  (`spec/models/studenthub_class_name_guards_spec.rb`), the rest are by design or false positives (packages already
  refuse `..`, `Marshal` deep copies, OAuth redirects, Rails-escaped KB links, `permit!` with `param_cleanup`). Every
  finding, its verdict and the reason: `.dev/security-review.md` (keep it up to date when fixing or ignoring one)
- Student Hub's own server code was reviewed by hand on 13 Oct (`.dev/security-review.md` → Manual review); the
  Claude Security plugin's scan can't run here (needs Claude Code workflows). Since then, assigning sites to
  managers needs full `admin`, and the Exchange password mask only works with the stored server and user
- Roles for customers only never carry `admin.*` permissions (decided 13 Oct): the 20261013120000 migration takes
  them off on every server (`Studenthub::CustomerRoles`). A ZAP scan on 13 Oct found one dev database's Customer
  role still had `admin.request_forms` (`.dev/security-review.md` → ZAP baseline, with how the scan was run)
- AI instructions are Student Hub's own (14 Oct): `CLAUDE.md` holds the rules, `.dev/ai-agent-instructions.md`
  (read as `.claude/CLAUDE.md`, `AGENTS.md` and `.github/copilot-instructions.md`) is the codebase guide. Removed
  from Zammad's setup: the GitLab workflow, the `code-reviewer` agent and the `work-on-issue` command; its Claude
  Code hooks go too (the lint hook ran a full type check after every reply). The
  security-guidance plugin was uninstalled: hooks are off here, so it never ran, and it reviews with Opus after
  every reply that changes code
- No `.dev/LOG.md` (14 Oct): commit messages are the record of what was done (`git log`); the old log is in the git
  history
- "Continue to mobile" stays out of the avatar menu for now (14 Oct): Taxil removed it and Student Hub doesn't use the
  mobile app (its spec still fails: NOTES → Tests that already fail)
- Message actions "Set to internal" / "Set to public" show the message's current state (14 Oct): an open lock while it
  is public, a closed lock while it is internal (Zammad shows the state the action sets)
- The admin pages' dark backgrounds and borders use the theme's `stone-500` (14 Oct), not the hand-typed `#1e293b`
  (235 places, the same colour today): a change to `stone-500` in the theme now recolours them with the rest of the app
- No "New desktop BETA UI … not ready for production use" pop-up after signing in (14 Oct): the new UI is the main
  one at `/` (`AppDesktop.vue` no longer calls Zammad's `useBetaUiDisclaimer`; the composable and its spec stay)
- The agents' dashboard is called "My overview" (15 Oct, was "My work"): it pairs with Team overview and shows
  figures about the agent's tickets rather than a to-do list
- My overview's "Your workload" card is called "Your tickets" (15 Oct): it shows the agent's assigned tickets, how
  many are in process and how they came in, not only how busy they are
- Vulnerable npm packages are fixed by refreshing them within the ranges their parents allow (`pnpm update <name>`),
  not with overrides (15 Oct): an override pins a version for good and is easily forgotten, so overrides stay for
  what a range can't do (the editor's one copy of each package in `pnpm-workspace.yaml`). Not `pnpm audit --fix`,
  which writes an override per advisory. Dependabot proposes security fixes only, no routine version bumps
- Rails 8.1 (15 Oct), as Rails 8.0's security support ended on 7 Oct 2026. `config.load_defaults` stays 8.0 until
  8.1's new framework defaults have been checked one by one. `benchmark` is in the Gemfile because Zammad's
  `delayed_job` fork needs it and Rails 8.1 no longer brings it in
- The classic UI is to be removed (15 Oct); what it alone still did moves to the new UI first. Moved: Scheduler jobs
  on users and organisations, every condition of the classic editor and every field of a template. Dropped, not
  moved: the BETA UI page and switch, the live chat console, the phone (CTI) log, Clearbit's setup and
  "subscribe me" on a ticket (contributors come through @mentions)
- The condition and action editor builds the fields of tickets, customers, users and organisations from Zammad's
  object manager (`attributes` of the automation options endpoint), with operators by field type as the classic
  editor does, so new fields need no code. The Templates editor uses the same action editor; what it doesn't know is
  kept as a "kept as it is" row (the separate kept-settings list is gone)
- Links to the classic UI's `#…` addresses (15 Oct): emails are fixed at the source (mail templates and Zammad's older
  services send new-UI addresses), not with aliases, because the new UI's `#…` translation runs only for signed-in
  pages and the sign-in check sends everyone else to the login page first. Invitation and reset tokens expire after a
  day, so links already sent need nothing. In-app links go to the new pages directly; old Knowledge Base and Data
  Privacy addresses get a redirect or alias for links stored elsewhere (help centre, activity stream, bookmarks)
- Classic UI switched off (15 Oct): `/app` and `/init` redirect to `/` (302, so an undo isn't stuck in caches) before
  any of its code is deleted, so the switch is one commit to revert (tag `before-classic-ui-off`). The code goes after
  a week or two without `/app` requests on production; `.dev/classic-ui-removal.md` lists what goes and what stays
- The new UI's BETA switch is removed (16 Oct), ahead of the classic UI's code, as it led only to the classic UI;
  Zammad's server side of it (settings, the user's flag, the feedback mutation) stays unused rather than changing the
  GraphQL schema
- No "Powered by Zammad" in the mobile app (16 Oct): its sign-in footer (`LoginFooter.vue`, the "Powered by Zammad"
  line and, with custom branding, Zammad's logo) is removed, as the new UI's sign-in page has none. The copyright
  headers in the code stay
- The mobile app follows design option 5 in a light theme on every page (16 Oct, chosen from five designs). The theme
  redefines the colour tokens Zammad's mobile components are built on ("black" is the page, "white" the text)
  instead of editing about 117 components, so it is one Student Hub stylesheet to undo; the accents take darker steps
  and the application colour, so "black" text on a coloured badge still reads. The username and password form sits
  behind "Admin / local login" under the Microsoft button, and is open from the start when no third-party sign-in is
  on, so nobody is locked out. The heading stays the product name, as a "Sign in" heading next to the "Sign in"
  button is ambiguous for screen readers and Zammad's tests. The Knowledge Base tile opens the new UI's, as the mobile
  app has none. The application colour helper moved from the new UI to shared code for this second user
- No Zammad name in the mobile app (16 Oct): the account page's "This is Zammad version …" section and "You can help
  translating Zammad" hint are removed, and the app installs as "Student Hub" (a fixed name, as the home-screen label
  must be short; the full name still comes from the organisation or product name setting)
- Phones get the mobile app, computers and tablets the new UI (16 Oct), as the classic UI did before it was switched
  off; this replaces "Continue to mobile stays out of the avatar menu" (14 Oct), which is back for phones. "Phone" is
  Zammad's own check (`isMobile`, the device type from the browser), so tablets get the new UI. Only the pages the
  mobile app also has switch (home, sign-in, a ticket); links to the new UI's own pages (password reset, sign-up,
  Knowledge Base) stay put, so emails keep working. Opening `/mobile` directly shows it on any device and forgets an
  earlier "Continue to desktop", so a computer can check the mobile app and Zammad's mobile browser tests still run
- The mobile app's Playground is removed (16 Oct): a developer page of test fields that any signed-in student could open
  at `/mobile/playground` (its Home link showed in development only). The mobile app is mainly for students. The new
  UI's own Playground stays for now
- The mobile app is for students only (16 Oct): staff on a phone get the new UI with their staff tools, also right
  after signing in on the mobile sign-in page; computers may still open `/mobile` directly. Showing staff the student
  side of the mobile app was considered and dropped: it needs the Customer role (`ticket.customer`) on staff, and
  with the college organisations shared that role would let staff read every ticket of their college's students
- The mobile app's Home and Tickets follow design C1 with C3's latest ticket (16 Oct, chosen from five home designs
  and five variations of C): New request moves into the middle of the bottom menu and Tickets replaces Account;
  Notifications and the account move to the header. The Tickets tab lists only the student's own tickets (Zammad's
  "My Tickets" view), not "My Organization Tickets", because the college organisations are shared. Its filters and
  counts are worked out in the browser from up to 50 tickets at a time (Show more loads the next 50), as students
  have few. The design's topics and "Popular answers" wait: Student Hub's Knowledge Base API is for staff only
  ("students read the public help center"), so Home links to the help center until a students' source is decided
- "My Tickets" lists a student's tickets in every state but merged (16 Oct), as a condition ("state is not merged")
  rather than a list of states, so states admins add later show up too; Zammad's seeded list had left out
  "3. In Progress", "4.1 Pending / On Hold" and "5. Resolved". The Tickets tab sorts by state in the order a ticket
  goes through, grouped as its labels are (Assigned, In Progress and On Hold are all "In progress")
- The mobile app gets its own admin page, **Mobile app** under Manage (16 Oct), so more of the app can be set there
  later; its first part is the quick links on Home. They are a setting (no table: at most 8, saved as one list
  through Zammad's settings API, which checks the new `admin.mobile_app` permission) and only http and https
  addresses are allowed, as the app opens them; each card shows the site's name, so students see where it leads
- The mobile app's ticket screen is a chat for students (16 Oct, design 1 of five, with a "Did this solve your
  problem?" card added): a message is sent from a box at the bottom through Student Hub's REST endpoint, not Zammad's
  ticket form, so it takes one tap and no Save; files still go through Zammad's reply form, which handles uploads. A
  message to a resolved or closed request reopens it with the same rules as the new UI's "Still not fixed? Reopen".
  "Yes" on a closed request with no rating waiting is not saved, so the card asks again next time. `studenthubApi` and
  the student ticket types moved to `app/frontend/shared/utils/`, as the two apps may not import each other's files
- The mobile app's Home lists **Popular answers** chosen by admins under Manage → Mobile app (17 Oct), in place of
  design C1's topics and answers. Only answers published in the help center can be chosen or shown, as students read
  the help center and Student Hub's Knowledge Base API is for staff; the choice is stored as answer IDs and Home asks
  the server for those still published, so an answer made internal later never reaches students. Each opens its
  help center page in the same tab (quick links, other websites, open a new one)
- Students raise a request in the mobile app as a chat (17 Oct; design B "Chat" from five wizard designs, with E's
  search): a new conversation each time, one question at a time, and typing searches every sub-category so a
  student who knows what they need skips the category. It asks for the same things as the new UI's wizard and sends
  the ticket the same way (Zammad's ticket create mutation, the group from Zammad's own ticket form), so the server's
  checks and the request forms apply unchanged; a request form's questions are asked one by one instead of as a
  form. Staff keep Zammad's form. The request form types moved to shared code for it
- The mobile app has its own Knowledge Base, **Help articles** (17 Oct; design 1 "Topics" from five designs, without
  its Popular answers, which stay on Home): topics as tiles, a topic's sub-topics and answers, search, and the answer
  in the app. This replaces opening the help center from Home and Popular answers. It shows only what the help
  center publishes, through its own endpoints (the new UI's Knowledge Base API stays staff-only); its search runs
  Zammad's Knowledge Base search without a user, as given one it also finds drafts and internal answers for
  Knowledge Base editors. "Still need help?" opens the request chat without a category, as Knowledge Base topics are
  not request categories
- Students say whether an answer helped (17 Oct): one vote per student and answer, which they may change, stored by
  Student Hub (`studenthub_answer_feedbacks`), as Zammad keeps no such feedback; staff see the counts on the answer in
  the new UI, not who voted. Buttons that stored nothing would be a fake control. Votes go with the student, removed
  before Zammad's own check that refuses to delete a user other records still point at
- Students' search in the mobile app puts what answers the question first (17 Oct): help articles, then the request
  types to raise, then their own tickets; a section without matches is hidden, so with no article the request types
  lead. Request types are always shown when they match, also below articles. Staff keep Zammad's search. Tickets come
  from Zammad's ticket search (with message text), kept to the student's own as on the Tickets tab. Help article
  results named after the words come before those that only mention them (Elasticsearch ranks a long answer that
  mentions a word above a short one named after it)
- The mobile Tickets tab has no All / Open / Waiting for you / Closed buttons any more (17 Oct, the user's choice):
  search and Sort by are enough, and each card already says where the ticket stands. Home's "Your latest ticket"
  is the newest ticket the student raised, not the one changed last. Zammad's My Tickets view here is grouped by
  state (an admin's choice, kept for the new UI's list), and its grouping comes before any order asked for, so Home
  asks a small Student Hub endpoint for the newest (`GET /api/v1/studenthub/customer_tickets/latest`, sorted on the
  server, correct however many tickets there are) and the Tickets tab sorts the tickets it has loaded itself
- Students get notifications in the app (17 Oct; the restyle plus notifications, chosen over the restyle alone):
  Zammad's go to staff only, so the bell in the mobile app's header never lit up for students. Student Hub's own async
  transaction backend tells the ticket's customer (students only; staff keep Zammad's) when the team replies (not
  internal notes or the system's automatic emails) and when the ticket moves to another stage as the Tickets tab shows
  them, one notification per change. They say "The team replied", as students may not see staff's full names and the
  chat shows none. Closing a ticket doesn't mark them read, as that is the news. The page has the app's header and
  cards (design C1) and replaces Zammad's mobile notification page, whose tests now run on it
